# Как ведём работу

Проект небольшой и делается вдвоём, поэтому процесс ровно такой, какой нужен,
чтобы не мешать друг другу — и ни шага больше.

## Тикеты

[GitHub Issues](https://github.com/lokehoke/my-spotify/issues). Отдельного трекера
нет намеренно: issue связывается с PR строкой `Closes #N` и закрывается мерджем
сама, так что статус не приходится вести руками в двух местах.

Лейблы:

- `area:api`, `area:catalog`, `area:audio`, `area:search`, `area:devops` — что
  трогаем. У задачи должен быть ровно один area-лейбл;
- `p1` — то, что делаем сейчас. Если `p1` больше пяти, приоритета нет ни у чего;
- `blocked` — ждёт чего-то извне, с пояснением в комментарии.

Статус живёт в борде Projects, а не в лейблах: две системы статусов всегда
расходятся.

## Ветки и PR

Ветка называется от номера issue — по ней потом понятно, зачем она была:

```
feat/12-catalog-models
fix/15-token-rotation-race
```

В описании PR — `Closes #12`. Ревью обязательно даже вдвоём: это единственный
момент, когда второй человек видит код до того, как он станет общим.

## Миграции

**Одна миграция на PR**, и перед `makemigrations` всегда `git pull --rebase`.
Иначе оба получают `0007_*` и Django молча ловит две головы. CI это поймает
(`makemigrations --check` в [ci.yml](.github/workflows/ci.yml)), но чинить
руками неприятно.

База у каждого своя (см. ниже), поэтому чужая миграция не ломает твою работу
в момент, когда ты её не ждал.

## Общий стенд

Тяжёлое состояние живёт на одной машине, а приложение каждый поднимает у себя.
Делится то, что дорого заводить дважды — аудио; Redis и Meilisearch у каждого
свои, иначе твою Celery-задачу выполнит воркер соседа на своём коде.

Поднять стенд (один раз на машине):

```bash
docker compose -f compose.shared.yml up -d
```

Появляются:

- **Postgres** на `5432` с отдельной базой на каждого — список в `DEV_DATABASES`,
  создаются при первой инициализации тома;
- **MinIO** на `9000` (API) и `9001` (консоль) с бакетами `masters`, `audio`,
  `images` — замена Cloudflare R2 на время разработки (ARCHITECTURE.md §4.5).

Свой app-стек поднимайте с третьим override-файлом — он выключает локальный
Postgres, который иначе конфликтовал бы со стендом по порту 5432:

```bash
docker compose -f docker-compose.yml -f compose.dev.yml -f compose.lan.yml up -d
```

В своём `.env` укажите адрес стенда и **имя своей базы**:

```
DATABASE_URL=postgres://myspotify:<pароль>@<хост-стенда>:5432/myspotify_<вы>
```

Хост стенда — `host.docker.internal`, если стенд поднят на этой же машине
(внутри контейнера `localhost` указывает на сам контейнер), иначе адрес той
машины в сети.

Перед тем как открыть стенд в сеть, смените `POSTGRES_PASSWORD`: дефолт из
`.env.example` годится только пока стенд виден с одной машины.

### Если Docker живёт в WSL

Обращайтесь к стенду по `127.0.0.1`, а не по `localhost`: релей WSL слушает
только IPv4, `localhost` резолвится сначала в `::1`, и соединение отваливается
без внятной ошибки.

Порты контейнеров в WSL по умолчанию не видны из локальной сети — при
`networkingMode=NAT` в `.wslconfig` они доступны только с самой машины. Чтобы
до стенда дошёл второй разработчик, нужен `networkingMode=mirrored` и
`wsl --shutdown`.
